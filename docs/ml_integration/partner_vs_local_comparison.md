## 2. Deep learning inventory

Three `torch`-based components exist. Framework is `torch==2.2.2` / `torchvision==0.17.2` throughout (per `requirements.txt`; loaded via the shared guarded importer `services/multimodal/torch_runtime.py`, which pins `OMP_NUM_THREADS=1`/`MKL_NUM_THREADS=1` to avoid an OpenMP crash from running alongside XGBoost in the same worker).

### 2.1 GraphSAGE-style graph net (`services/multimodal/graph_ai.py`)

- **Architecture** (`_GraphSAGEModel.create`, lines 62-121): 2-layer edge-gated neighbor-aggregation network. Per layer: `self_i = Linear(in,hidden)`, `neighbor_i = Linear(in,hidden)`, aggregation via a learned edge gate (`sigmoid(Linear(len(EDGE_RELATIONS)+2, 1))`) weighting neighbor features before mean-pooling, then `relu(self(x) + neighbor(agg))`. Output heads: `role_head` (6-way softmax over `beam/column/brace/plate/connection/other`), plus three sigmoid heads (`consistency`, `missing_label`, `incorrect_label`).
- **Inputs**: 19-dim node feature vector (5 continuous: normalized length/width/area/orientation/font_size, + 14-way one-hot node kind) and edge features (18-way one-hot relation + normalized distance + confidence).
- **Params**: ≈7.1K learnable parameters (hand-computed from layer shapes: input_dim≈19, hidden_dim=48). Consistent with the 35KB `graphsage_model.pt` on disk — the small file size is architecturally expected for this feature-dimension, **not** evidence of an incomplete/stub checkpoint by itself.
- **Training** (`train_graphsage`, lines 300-427): AdamW (lr=1e-3, weight_decay=1e-4), loss = cross-entropy(role) + 3×BCE(consistency/missing/incorrect), `epochs=25` default. **No train/validation split, no random seed set anywhere in this function or its callers.** Trains on every prepared graph sample every epoch.
- **Training data**: built by `neural_dataset.py::build_neural_training_samples()` from paired PDF/Excel projects (`list_training_pairs()`), `engineering_corrections.jsonl`, and approved-review CSVs — auto-labeled by matching PDF tokens to Excel ground truth, not hand-annotated.
- **Dataset size**: per the registry manifest (`backend/training/models/graph/graph_20260803_104505/manifest.json`), `supervised_count: 1812` labeled graph nodes across `class_count: 114` (this class count is the exact-section/family label space, not the model's own 6-way `ROLE_LABELS` — the manifest and the actual model target different label spaces, see below).
- **Checkpoint / promotion status — the key finding**: the `graph_20260803_104505` manifest and `backend/training/models/graph/registry.json` report `"accuracy": 0.5, "f1_weighted": 0.5`, `"promotion_status": "rejected"`, `"active_version": null`, note *"graph lane prepared; GCN/GraphSAGE deferred until denser coverage"*. **These numbers are hardcoded constants**, not measured metrics: `services/training_pipeline/trainers.py::train_graph_model()` (lines 254-292) literally writes `metrics = {"accuracy": 0.5, "f1_weighted": 0.5, "skipped": False, **readiness}` and never builds or evaluates a model — it only writes a `latest_features.json` feature-schema placeholder and immediately calls `mark_rejected(..., ["graph model is prepared but not production-promoted yet"])`. This registry/promotion system is **entirely disconnected** from the actual `graph_ai.py`/`train_graphsage()` code path that produces the real `graphsage_model.pt` used at inference. `train_graphsage()` itself returns only `{"path", "graphs", "epochs", "max_train_edges"}` — **no accuracy metric is ever computed for the checkpoint that is actually loaded**.
- **Inference path**: `enrich_graph_embeddings()` is called unconditionally from `services/multimodal/pipeline.py::run_multimodal_pipeline()` (line 159), which is called from `services/staged_pipeline.py` (imported by `routers/documents.py`) — i.e. **every document analysis goes through this**, gated only by "does `settings.graphsage_model_path` (`backend/training/graphsage_model.pt`, committed, 35KB) exist on disk," with zero reference to the registry's "rejected" status.
- **Downstream influence**: `ClassicalGraphEncoder` (`encoders.py`) prefers `graph_embedding`/`graph_confidence`/`graph_prediction` from this model over the deterministic fallback whenever present, feeding `modular_fusion.py`'s attention fusion and, if the fusion MLP checkpoint also exists, the learned-fusion candidate ranking.
- **Verdict**: **real, trained (backprop occurred, real weights), architecturally sound, but never evaluated** — and wired into every production prediction despite its own project's registry marking it "rejected."

### 2.2 MobileNetV3-Small geometry encoder (`services/multimodal/geometry_ai.py`)

- **Architecture**: `torchvision.models.mobilenet_v3_small(weights=MobileNet_V3_Small_Weights.DEFAULT)` with `model.classifier = nn.Identity()` — i.e. the **frozen, off-the-shelf ImageNet-pretrained** backbone used purely as a feature extractor. Output is mean-pooled into a 128-dim vector (`_compress_embedding`).
- **"Training"**: `build_geometry_embedding_index()` never trains or fine-tunes the CNN. It only crops labeled geometry regions from PDFs, runs them through the frozen backbone, and stores `(embedding, label)` pairs in `geometry_embedding_index.joblib` (464KB) for cosine-similarity nearest-neighbor lookup at inference. No gradient ever flows through the CNN.
- **Inference**: `enrich_geometry_embeddings()`, called unconditionally in `pipeline.py` (line 150), crops every geometry object with a bbox, embeds it, and does k-NN search (`search_geometry_embedding`) against the index. Falls back to `"vector_geometry"` (local's deterministic geometry features) if the index file doesn't exist.
- **Verdict**: **not a trained classifier at all** — it's a frozen pretrained ImageNet backbone driving a hand-built k-NN index. Calling this "geometry classification via deep learning" overstates it; it is closer to "reuse an off-the-shelf vision backbone as a similarity feature."

### 2.3 Fusion MLP (`services/multimodal/learned_fusion.py`)

- **Architecture** (`_create_model`): `Linear(input_dim,64) → ReLU → Dropout(0.1) → Linear(64,32) → ReLU → Linear(32,1)`, i.e. a small 3-layer scoring head over the concatenated encoder feature vector (`fused_vector`) plus per-modality scores (6 values: text/geometry/graph/ocr/layout/engineering_rules).
- **Training** (`train_fusion_model`): AdamW (lr=1e-3, weight_decay=1e-4), cross-entropy over which candidate in the list is correct, `epochs=100`. Split: `split = int(len(groups) * 0.8)`; `training = groups[:split]`, `calibration = groups[split:] or groups[-min(20, len(groups)):]` — **sequential (not shuffled, no seed), and drawn from the same document-iteration order as training**, so calibration samples from documents that also contributed to training are not excluded. Post-training, a separate temperature-scaling calibration step (`torch.optim.LBFGS` on `log_temperature`) fits `T` on that calibration slice.
- **Checkpoint**: 96KB `multimodal_fusion.pt`, consistent with this small parameter count.
- **Manifest disconnect**: same pattern as graph — `backend/training/models/fusion/registry.json` shows `active_version: null`, and `trainers.py::train_fusion_model()` (a *different* function, same name, in the old registry system) hardcodes `metrics = {"accuracy": 0.6, "f1_weighted": 0.6, ...}` without training or evaluating anything; it only computes attention-contribution priors (`contribution_priors.json`) from engineered features. The actual MLP trained by `learned_fusion.py::train_fusion_model()` has no recorded accuracy anywhere.
- **Inference**: `predict_learned_fusion()` is called unconditionally from `modular_fusion.py::UnifiedMultimodalFusion.predict()` whenever `multimodal_fusion.pt` exists, and when it returns a result it **overrides** the deterministic attention-fusion ranking (`scored = learned["candidate_scores"]`) and directly sets the final `section`/`confidence` returned to the caller. This is the one component that can directly change which shape gets predicted, not just contribute a feature.
- **Verdict**: **real, trained, and the highest-impact of the three** (it can override the final label), but calibrated on too small/non-independent a sample to trust, and — like the graph net — has no held-out accuracy number anywhere in the repo.

### 2.4 Cross-cutting findings

- **Two disconnected training/tracking systems.** `services/training_pipeline/trainers.py` + `model_registry.py` (pre-existing, extended by partner to nominally cover geometry/graph/fusion) writes versioned manifests with **hardcoded placeholder metrics** and explicit "not production-promoted" rejections. `training/train_neural_models.py` + `services/training_pipeline/neural_dataset.py` (new) is the system that actually trains and writes the `.pt`/`.joblib` files loaded at inference, and it has no promotion gate and no accuracy computation at all. The inference code (`graph_ai.py`, `geometry_ai.py`, `learned_fusion.py`) checks only `Path.exists()` on the fixed `settings.*_path` — it is unaware of either registry's promotion status.
- **exact_section / family_classifier are not deep learning.** `exact_section_model.joblib` is `character_tfidf_cosine_retrieval` (classical TF-IDF + cosine, per `exact_section_model_metadata.json`); `family_classifier` is XGBoost (`model_metadata.json`: `"model": "XGBoost"`, `accuracy: 0.9924` on a real confusion matrix — this one *is* a real, evaluated, pre-existing classical model, now retrained/re-versioned by partner but not new DL). `exact_section`'s reported `accuracy: 1.0, f1_weighted: 1.0` (2,299 exact labels → 60,442 corruption/augmentation variants) is a near-certain **circular-evaluation artifact**: a nearest-neighbor/retrieval model evaluated on variants of the same strings it indexed will trivially score 1.0; this is not evidence of real-world accuracy.
- **No secrets found.** Grepped all `manifest.json`/`registry.json`/`*_metadata.json` files and the large CSVs' headers under `backend/training/` for API keys, passwords, connection strings, and PEM headers — none found. Manifest `artifacts` paths do leak the partner's local absolute filesystem path (`/Users/hibareda/Desktop/ai-dynamic-regex/...`), which is a minor information-hygiene issue (developer username/machine layout), not a credential.

## 4. Integration recommendation

**Decisive summary: merging this commit as-is, with the DL pipeline defaulting to "on," would be premature.** Not because the code is badly written — the GraphSAGE and fusion-MLP implementations are competent, readable torch code with sensible architectures for their tiny feature dimensions — but because of three independent, concrete problems that each need to be resolved first, not papered over:

1. **The models that actually run in production have never been evaluated.** `graphsage_model.pt` and `multimodal_fusion.pt` are loaded and used on every single document analysis (`pipeline.py` calls `enrich_graph_embeddings`/`enrich_geometry_embeddings` unconditionally, and `modular_fusion.py` lets the fusion MLP override the final predicted label whenever its checkpoint file exists), yet there is no code path anywhere in the repo that computes a held-out accuracy for either checkpoint. The only "accuracy" numbers that exist for these lanes (`0.5`/`0.6` in the registry manifests) are hardcoded literals in `trainers.py`, unconnected to the real checkpoints, and the registry that does track them explicitly marked them `"rejected"`/`"not production-promoted"` — a promotion decision the runtime code silently ignores. Shipping this means every user of the analysis pipeline is getting predictions influenced by an unevaluated model that its own project's own governance system rejected.
2. **Two training/versioning systems disagree with each other and neither is authoritative for what's actually running.** This needs to be unified (one registry, one promotion gate, and the inference loader should respect it) before more models are added to either side.
3. **`requirements.txt` does not install cleanly on this machine** (`xgboost==3.3.0` has no Windows/Python-3.11 wheel), and the `numpy`/`scipy` downgrade required for `torch==2.2.2` is a repo-wide constraint change, not a scoped addition — every existing LightGBM/XGBoost/sklearn/pandas/shapely consumer inherits it. That needs a resolution (e.g., upgrade the torch pin to a numpy-2.x-compatible release, or fully isolate the torch-dependent code into an optional extra) before this is a safe default dependency set.

**What to keep from partner**: the text/table/schedule extraction stack (`pdf_parser.py`, `token_extractor.py`, `document_intelligence.py`) is new surface area local doesn't have and is largely independent of the DL question — worth evaluating on its own merits, separately from the neural components. The `ClassicalTextEncoder`'s reuse of the existing TF-IDF vectorizer is low-risk and can merge freely. The versioned-registry *pattern* (`manifest.json`/`registry.json`, checksums, `parent_version`) is worth keeping and extending to actually cover the `.pt`/`.joblib` files, once the hardcoded-metrics problem is fixed.

**What to keep from local**: `label_reconstruction/` (damaged-label corruption taxonomy + deterministic candidate generation) has no partner equivalent at all and should not be put at risk by any merge. The calibration honesty policy (`MIN_CALIBRATION_SAMPLES = 50`, refuse rather than fabricate) is a real safety property partner's temperature-scaling calibration doesn't match and should be the standard either side's confidence output is held to. The `ml_association` isolation pattern (feature flag off by default + a structural test proving the production pipeline can't import it) is exactly the right template for how partner's DL components should have been introduced, and is the template to apply retroactively to `graph_ai.py`/`geometry_ai.py`/`learned_fusion.py` before any merge: land them **behind a flag, defaulting off**, with an equivalent "not wired into production" test, until they have real held-out accuracy numbers.

**Conflicts**: `structural_graph.py` and `graph_builder.py` (local, uncommitted) vs. `graph_ai.py` (partner) are **complementary, not a hard conflict** — local's changes are ID-determinism and diagnostics on the deterministic rule-based graph *construction* step that both sides share as an input; partner's `graph_ai.py` consumes that same graph structure and adds a learned *scoring* layer on top. They don't touch the same functions and can coexist; the integration work is deciding whether the learned layer's output is trusted, not resolving a code conflict. `geometry_extractor.py` (local, uncommitted, dense-page-cap audit) is not touched by partner at all, so merging partner's commit as-is would silently reintroduce the exact defect local just diagnosed and started fixing — this should be called out explicitly to whoever performs the merge.

**Suitability for the damaged-steel-label-reconstruction task specifically**: none of partner's three DL components are well-matched to this task as they stand. The GraphSAGE net's role classes (`beam/column/brace/plate/connection/other`) target structural-role classification, not label-text reconstruction. The MobileNet geometry encoder is a frozen generic-image feature extractor with no shape-family/section-specific training. The fusion MLP could in principle learn to weight `label_reconstruction`'s candidate set once that data exists as a labeled training signal, but that would require building a fusion training set from `label_reconstruction`'s corruption/candidate output — which does not exist yet on either side. The nearest usable hook is `ml_association`'s candidate-set design plus the fusion MLP's architecture as a *template* for a future learned re-ranker over `label_reconstruction`'s candidates, not any of partner's checkpoints as delivered.

## 5. Selective-integration plan (Part 13) — what to port instead of merging all 177 files

`origin/main` remains unmerged (this section is a plan, not an action taken). Rather than a single all-177-files merge commit, the recommended path is several small, independently-reviewable ports, in this order:

### 5.1 Dependency/artifact blockers to resolve FIRST, before porting any code

1. **`xgboost==3.3.0` pin is broken on Windows/Python 3.11** — no wheel exists for that combination on PyPI (newest available is `3.2.0`). This alone makes `pip install -r backend/requirements.txt` fail on this machine as committed. Fix: either re-pin to `xgboost==3.2.0` (verify it still satisfies whatever partner's code needs) or document the requirement as macOS/Linux-only and split platform-specific pins.
2. **`numpy`/`scipy` downgrade is repo-wide, not scoped to the DL code.** `numpy==2.5.1→1.26.4` and `scipy==1.18.0→1.13.1` affect every existing LightGBM/XGBoost/sklearn/pandas/shapely consumer, not just `torch`. Fix: either find a `torch` release compatible with numpy 2.x (torch 2.3+ generally supports it), or isolate the torch-dependent modules (`services/multimodal/*_ai.py`, `learned_fusion.py`, `torch_runtime.py`) behind an optional extras group (`pip install .[multimodal]`) so the base install stays on current pins.
3. **~150MB of binary/CSV artifacts committed directly to git**, with near-duplicate copies: `exact_section_model.joblib` (~35MB) exists identically in THREE places (`backend/training/exact_section_model.joblib` plus two versioned experiment folders); `best_model.pkl` (~4MB) exists in two places. Fix before porting: keep exactly one copy per artifact — either the versioned-registry copy (preferred, matches the existing `manifest.json`/`registry.json` pattern) or the top-level live-deployment alias (`model_registry.promote_to_live_paths` already exists for this exact purpose), never both duplicated in history. Consider `git-lfs` or excluding regenerable artifacts from git entirely (regenerate via `train_neural_models.py` post-checkout) rather than committing large binaries as plain blobs.
4. **`.pt` checkpoint governance**: neither `graphsage_model.pt` nor `multimodal_fusion.pt` is versioned through `model_registry` today (see `docs/ml_integration/partner_dl_governance_plan.md`). Before porting the code that loads them, wire their save/load path through `model_registry.register_candidate_model`/`get_active_model` so "is this checkpoint approved" is a real, checkable question instead of "does a file exist at a fixed path."
5. **Real client PDFs/Excel already in git history** since the Initial commit (pre-existing, not partner's doing) — partner's commit correctly deletes them from tracking and adds `.gitignore` rules preventing recommission, but deletion doesn't purge history. A `git filter-repo`/BFG history rewrite is a separate, high-blast-radius decision requiring explicit user sign-off — flagged here, not attempted.

### 5.2 What to port, and in what order, once the above is resolved

1. **Port first, low risk**: `pdf_parser.py`/`token_extractor.py`/`document_intelligence.py` (new text/table/schedule extraction — additive, doesn't touch anything local's Phase 0-2.6 work depends on) and the `ClassicalTextEncoder`'s reuse of the existing TF-IDF vectorizer. Land alongside local's already-fixed `geometry_extractor.py`/`graph_builder.py` (deterministic IDs, dense-page audit) — NOT partner's untouched pre-audit versions, to avoid reintroducing the zero-area-drop defect local already diagnosed.
2. **Port second, medium risk**: the versioned-registry *pattern* extension (`manifest.json`/`registry.json` for `geometry`/`graph`/`fusion` families) — but rewire it so `trainers.py`'s hardcoded `metrics = {"accuracy": 0.5, ...}` literals are replaced with real computed metrics against a genuinely held-out (document-grouped, not positional-split) evaluation set, per the governance checklist.
3. **Port last, highest risk, requires the governance checklist fully satisfied first**: `graph_ai.py`, `geometry_ai.py`, `learned_fusion.py` themselves — land behind a feature flag defaulting OFF (mirroring `ML_ASSOCIATION_DATASET_ENABLED`/`ML_LABEL_RANKER_ENABLED`), with a `test_multimodal_dl_not_wired_into_production.py`-style structural test, and do not flip the flag until each checkpoint has a real, document-grouped held-out accuracy number recorded through `model_registry`.

### 5.3 What NOT to port as-is
