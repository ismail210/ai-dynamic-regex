# Unresolved Questions — Phase 2

Carries forward anything from `docs/geometry_graph_audit/09_open_questions.md` that Phase 2's design decisions touch, plus new questions raised specifically by building this package. None of these block Phase 2's own acceptance criteria (all met on synthetic fixtures — see `next_phase_recommendation.md`), but several should be resolved with real project data and/or a structural-domain expert before Phase 3 (frozen baselines) or Phase 4 (the first trained ranker) begin.

## Domain questions (need a structural-domain expert, not more code)

1. **Grid-line visual cues.** `annotation_guidelines.md` tells reviewers the pipeline cannot currently distinguish a grid line from a beam by geometry alone. Which cues (bubbles, dash patterns, regular spacing, line weight, extension beyond framing) should a future geometry-classification model actually use? Carried over verbatim from the deep-research report's domain questionnaire (`docs/geometry_graph_audit/06_research_findings.md`) — still unanswered.
2. **"Typical" (`callout_scope=typical`) scope boundaries.** What determines where a "TYP" callout's applicability ends? Untouched by Phase 2; reviewers are told to use their own judgment and flag `unknown` when unsure.
3. **Repeated labels: one entity or many?** Should multiple on-page instances of the same label text be treated as independent `text_entity_id`s (as Phase 2 currently does — each token gets its own stable ID from `token_id`) or as one logical designation with multiple occurrences? Phase 2's schema supports either interpretation at the review layer (`callout_scope=repeated` plus multiple separate `ReviewedOutcome`s, one per token instance) but does not itself decide which modeling choice is "correct" for training purposes.
4. **Wrong-adjacent-member severity.** The deep-research report explicitly recommends a severity matrix before model promotion (Phase 3+). Phase 2 records enough provenance (`candidate_generation_miss`, full candidate ranks) to compute this later, but does not attempt to define acceptable error rates itself.
5. **Nonstandard/built-up members, joists, misc. metals.** Not addressed by this phase's schema beyond `label_type`/`parsed_family` being free-form strings — no dedicated handling.

## Technical/design questions raised by this phase's own implementation

6. **`graph_degree`/`graph_relation_summary` are geometry-candidate-centric, not label-centric.** `candidate_dataset._graph_context_for_node` reports the *geometry candidate's* graph connectivity (how structurally connected that geometry node is), not the label's. This was a deliberate but somewhat arbitrary choice (geometry connectivity seemed more directly useful for "is this candidate structurally plausible" than label connectivity) — worth revisiting once real review data shows which framing correlates better with reviewer decisions.
7. **`leader_path_ids` is always empty in this phase.** `spatial_index.nearest_geometry_candidates` resolves *through* a leader to find its real target (`leader_endpoint_resolved` in `candidate_generation_sources`) but does not expose *which* leader node did the resolving back to the caller. `candidate_dataset.py` therefore cannot populate a specific `leader_path_id` (`identifiers.leader_path_id` exists and is tested but currently unused by the dataset builder). Fixing this would mean extending `spatial_index.SpatialCandidate` to carry a `resolved_via` field — a small, contained change to an already-tested Phase 1 module, deliberately deferred rather than made under this phase's time budget. `relationship.leader_support_evidence` (boolean) is populated correctly today; only the specific path ID is missing.
8. **`current_heuristic_score`/`rank` are only ever populated for the one candidate production's greedy heuristic picked.** This accurately reflects that the current heuristic doesn't rank alternatives (see `schema.md`) — but it does mean a future model that wants "the heuristic's implied score for every candidate, not just its pick" would need a different, additional computation (e.g., recomputing `1/(1+distance)` for every candidate, not just the winner). Not implemented here since it would blur "what production actually did" with "what we could retroactively compute it would have scored" — flagged rather than silently added.
9. **No true endpoint-level geometry.** `feature_builder.py`'s `nearest_endpoint_distance` and the leader-path overlay in `review_export.py` both approximate using bounding boxes, since raw line points are not carried onto graph/geometry-evidence nodes (`docs/geometry_graph_audit/04_graph_audit.md §13`). Both are documented in-code as approximations, not exact endpoint math.
10. **Real `project_id`/`document_id` assignment convention.** Phase 2 requires these as caller-supplied inputs rather than inventing project-grouping logic (no such concept exists elsewhere in the repository — `docs/geometry_graph_audit/09_open_questions.md`). Whoever operationalizes this workflow needs to decide the actual convention (see `review_workflow.md`'s suggested default).

## Phase 2.5 domain-expert questionnaire (sanitized real examples)

Real, concrete cases found during the pilot that need a licensed structural-domain expert's judgment, not a guess. Project names are never used; pages are referenced by pilot ID (`real_project_pilot_manifest.json`).

13. **Does one label validly apply to multiple visible members?** On `pilot_10` (257 engineering tokens on one page, several designations repeated 10-34 times in close proximity, e.g. one repeated 34 times, another 32 times), it is visually obvious that many physically distinct parallel members share an identical label — but whether *this specific system's* review process should record that as one label with `callout_scope=multiple`/`repeated` pointing at several targets, or as independently-reviewed instances, needs expert/business input, not an assumption baked into the schema.
14. **How should "typical member" labels propagate?** Not directly observed with an explicit "TYP" marker in the pages sampled during this pilot, but the repeated-designation pattern above (question 13) may be exactly what a "typical" convention looks like once a domain expert examines the actual sheet notes.
15. **How do grid lines differ from beam lines in cues actually present on these real sheets?** Still unanswered — the pipeline has no grid-line concept (`docs/geometry_graph_audit/03_geometry_audit.md §8`), and this pilot did not attempt to manually distinguish them either.
16. **How do detail boundaries affect association?** `pilot_04`/`pilot_05` (both from the same project, one moderate-density detail page and one very dense one) are visually distinct "details" on a multi-detail-per-page layout typical of this corpus, but the pipeline has no region/detail-boundary concept (confirmed again in Phase 2.5 — `region_id` stayed `None` on every real row, same as the synthetic-fixture finding).
17. **How do leader arrows identify targets, and how reliable is bbox-corner endpoint estimation on real leaders?** Directly observed and partially answered by this pilot: on `pilot_05`, a real label's current-heuristic-selected "target" was the leader stroke itself (confirmed both in raw data and by direct visual inspection of a rendered crop — see `real_project_error_taxonomy.md`), and population-wide across all 11 pilot pages, this happened for **243 of 843 heuristic-selected groups (28.8%)**. This is now a verified, quantified real-data finding, not a hypothesis — but *how* to correctly resolve leader targets when a real leader has a dog-legged/multi-segment path (not the straight 2-point segment this pilot's bbox-corner approximation assumes) still needs verification against real dog-legged leaders, which were not specifically isolated and inspected in this pass.
18. **Does label orientation/rotation carry meaning?** Not investigated in this pilot. All 262 real pages had page-level rotation 0, but individual text spans may still carry non-zero rotation (vertical/rotated callouts) — `text_rotation` is captured in the schema (`LabelEvidence.text_rotation`) but not analyzed for semantic meaning in this pass.
19. **When should a member schedule override a plan label?** Not investigated — `real_project_excel_assessment.md` found the schedules are not reliably linkable to specific plan-view geometry (only a coarse, unverified sheet-level linkage), so this question cannot yet be operationalized even if a domain expert answers it in principle.
20. **Commercial severity of selecting the wrong adjacent member.** Still entirely a policy question requiring the takeoff business owner (per `docs/geometry_graph_audit/06_research_findings.md`'s original ask) — Phase 2.5 did not attempt to assign severity, only to quantify how often the *current* heuristic makes a specific, identifiable class of error (leader-as-target).
21. **Acceptable association error rate by drawing type.** Not investigated — would require reviewed ground truth this pilot deliberately did not fabricate (see `real_project_annotation_status.md`).
22. **May a member label validly point to a centerline, an outline, or a detail profile (rather than a single "the" geometry object)?** Directly relevant to `real_project_error_taxonomy.md`'s finding that a page-spanning filled rectangle (a sheet border) was returned as a plausible-looking candidate before the Phase 2.5 fix — a domain expert's answer to "what does a label legitimately point at" would sharpen the area-shaped filter's threshold, which was chosen geometrically (both bbox dimensions large relative to search radius), not from domain input.
23. **How should section/detail references be represented?** Not addressed — `CalloutScope.DETAIL_REFERENCE`/`SCHEDULE_REFERENCE` exist in the enum (Phase 2) but no pilot page was reviewed against them (no human review occurred in Phase 2.5 — see `real_project_annotation_status.md`).
24. **Which Excel outputs are authoritative?** Partially answered by `real_project_excel_assessment.md`: the per-shape `ProjectHome` rollup and the per-row schedules are internally consistent within one workbook, but nothing establishes whether the schedules are themselves the authoritative source of truth or a prior (possibly imperfect) takeoff output — this is a business-process question, not something derivable from the files alone.
